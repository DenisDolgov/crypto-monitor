# 0001. Схема нормализованного курса и реестр валют

- **Статус:** Proposed
- **Дата:** 2026-11-17
- **Связанные issue:** MYSP-2 (§4, AC-14, AC-16, AC-17, AC-21), MYSP-3
- **Заменяет / заменено:** —

## Контекст

Инвентаризатор читает разнородные фиды обменников (собственная XML-схема, BestChange-совместимый XML, CSV, JSON) и должен свести их к одной записи курса. Эта запись — не только формат отчёта: на неё будут опираться хранилище, расписание опроса и алерты в следующих issue. Поэтому схема фиксируется сейчас, а не «когда понадобится».

Требования, которые уже приняты:

- направления в MVP — `USDT/RUB` и `BTC/RUB`, но нормализация обязана переживать любую пару, которую отдаёт фид, включая металлы и экзотику; `base`/`quote` — свободные коды с реестром (код, имя, тип), а не enum;
- котировка только текущая, истории нет;
- курс — «как опубликован», без учёта комиссий и без пересчёта в нетто;
- валидный XML без извлекаемых курсов — это `error`, а не `ok`;
- отсутствие значения — `null`, ноль не подставляется;
- точность курса не теряется (не менее 8 значащих цифр).

Что здесь решается: состав и типы полей записи, правила приведения чисел, семантика направления и стороны сделки, поведение при неизвестной валюте, ссылка на сырые данные.

## Варианты представления чисел

1. **`float` в JSON** — привычно, но двоичное округление: `78.5` может стать `78.49999999999999`, а сложение курсов и резервов даёт дрейф. Для финансового поля это скрытый дефект, который всплывёт в алертах.
2. **Строка с фиксированным масштабом (`"78.50000000"`)** — детерминированно, но навязывает масштаб, которого у фида может не быть (у кого-то 2 знака, у кого-то 8), и провоцирует «дописывание» нулей, неотличимое от реальной точности.
3. **Строка с исходной точностью, внутренне `Decimal`** — значение в JSON совпадает с опубликованным, сравнение и арифметика идут в `Decimal`, округление только при отображении в Markdown.

Выбран третий вариант: JSON — строка `^-?(0|[1-9]\d*)(\.\d+)?$` без экспоненты и разделителей групп, внутри — `decimal.Decimal` с контекстом `prec=28`. Переход в `float` запрещён на всём пути (включая тесты и отчёты).

## Решение: запись курса

Одна запись — один словарь в `reports/feeds.json` (`domains[].examples[]`) и в будущем одна строка хранилища. Поля фиксированы, имена не меняются без нового ADR.

| Поле | JSON | Обяз. | Правило |
| --- | --- | --- | --- |
| `exchanger_domain` | string | да | домен из `data/exchangers.csv`, lowercase, ASCII/punycode. Ключ обменника, а не URL |
| `base` | string | да | код актива из реестра, верхний регистр; актив, за 1 единицу которого выражен курс |
| `quote` | string | да | код валюты из реестра, верхний регистр; валюта, в которой выражен курс; `base != quote` |
| `rate` | string (decimal) | да | **сколько `quote` дают за 1 `base`**, `> 0`, конечное |
| `side` | string | нет | чья это сторона: `client_buys_base` (клиент покупает base), `client_sells_base` (клиент продаёт base), `unknown` (по умолчанию); `null` не используется |
| `reserve` | string (decimal) \| null | нет | резерв в единицах `quote`, `>= 0` |
| `reserve_derived` | bool | да | `true`, если резерв был в `base` и приведён умножением на `rate` |
| `min_amount`, `max_amount` | string (decimal) \| null | нет | лимиты в единицах `base`, `>= 0`; `min <= max`, если заданы оба |
| `fee_percent` | string (decimal) \| null | нет | комиссия как опубликована, `[-100, 100]`; курс не пересчитывается |
| `updated_at` | string (RFC 3339, UTC) \| null | нет | дата из фида; отсутствует — `null`, `fetched_at` не подставляется |
| `fetched_at` | string (RFC 3339, UTC) | да | время получения документа |
| `direction` | string | да | производное `"BASE/QUOTE"`, для фильтра MVP и группировки |
| `rate_derived` | string | да | `direct` — курс взят в ориентации фида, `inverted` — получен как `1/published` |
| `source_url` | string | да | конечный URL документа, из которого извлечена строка (`final_url`) |
| `raw` | object | да | ссылка на сырые данные, см. ниже |
| `warnings` | string[] | да | предупреждения по строке, `[]` если нет |

`raw` — не тело ответа, а его опознавательный набор: `{sha256, size_bytes, format, encoding, http_status, content_type, gzip}`. Тело по умолчанию не сохраняется: инвентаризация гоняется по чужим публичным документам, хранить их копии ни к чему, а `sha256` (от распакованного тела) позволяет проверить, что повторный запрос отдал то же самое. Флаг `--keep-raw` в MVP не реализуется; если появится, тела лягут в `reports/raw/<sha256>.<ext>` и ADR будет дополнен.

`side` — добавка к минимальному набору MYSP-2. Без неё `USDT/RUB = 78.5` неоднозначен: это цена покупки или продажи? Для отчёта о покрытии это терпимо, для сравнения курсов и алертов — нет, а схема должна пережить переход к ним. Поле опциональное: если фид не даёт различить сторону, ставится `unknown`, строка не отбрасывается.

## Решение: резерв и даты

- `reserve` принимается только в `quote` либо в `base`. Резерв в `base` приводится к `quote` умножением на `rate` с `reserve_derived: true`.
- Если резерв объявлен в третьей валюте (например, `USD` при паре `BTC/RUB`), он **не** пересчитывается по чужому курсу: `reserve = null`, warning `reserve_currency_mismatch`. Кросс-курсы — не задача инвентаризатора.
- `updated_at` принимает: ISO 8601 с зоной или без (`2026-11-17T08:00:00Z`, `2026-11-17 08:00:00`, `2026-11-17T08:00:00+03:00`), `DD.MM.YYYY HH:MM[:SS]` и unix-время в секундах. Значение без зоны считается UTC. В JSON всегда RFC 3339 UTC с `Z`.
- Неразбираемая дата не роняет строку: `updated_at = null`, warning `invalid_updated_at`. Подставлять `fetched_at` вместо даты фида запрещено (MYSP-2 §4).
- Дата в будущем относительно `fetched_at` сохраняется как опубликована с warning `updated_at_in_future`: это сигнал о фиде, который врёт, а не повод молча править данные.

## Решение: направление и ориентация

- `rate` — всегда «quote за 1 base». Других трактовок нет.
- Ориентация берётся из фида: `from` → `base`, `to` → `quote`, поля `in`/`out` (сколько отдал / сколько получил) дают `rate = out / in`, `rate_derived = direct`.
- Если фид публикует обратную величину («сколько base за 1 quote») или даёт пару в обратном порядке с явной семантикой — курс инвертируется (`rate = 1 / published`), `rate_derived = inverted`. Инверсия выполняется в `Decimal`, а не в `float`.
- Пары **не переупорядочиваются** к «каноническому» виду (например, fiat всегда quote): порядок остаётся как в фиде. Причины: (а) переупорядочивание требует правила «что считать главным» для каждой экзотической пары, которого у нас нет; (б) `examples` в отчёте должны читаться против опубликованного документа; (в) сравнение направлений — задача потребителя, у нас есть `direction` и `rate_derived`.
- `base == quote` после нормализации — строка отбрасывается (`invalid_direction`).
- Фильтр MVP сравнивает направления с учётом ориентации: `USDT/RUB` и `RUB/USDT` (инвертированный) — одно направление.

## Решение: реестр валют

`data/currencies.csv`, UTF-8, разделитель `,`, заголовок:

| Колонка | Правило |
| --- | --- |
| `code` | `^[A-Z0-9]{2,10}$`, уникален. Криптовалюта — общепринятый тикер (`BTC`, `USDT`), металл — `XAU`/`XAG` |
| `name` | человекочитаемое имя, свободный текст |
| `type` | `fiat`, `crypto` или `metal` |
| `aliases` | список идентификаторов из фидов, разделённых вертикальной чертой (`USDTTRC`, `USDT-TRC20`, `SberbankRUB`); сравнение без учёта регистра и пробелов по краям |

Правила:

- реестр — данные, а не код: правка реестра не требует правки парсера, но требует ревью;
- `type` берётся только из реестра; фид не может его задать;
- `metal` — третье значение типа, потому что металлы (`XAU`, `XAG`) в фидах встречаются, а `fiat`/`crypto` для них ложь. Это расширение формулировки «тип: fiat/crypto» из решения человека; если третье значение не нужно, металлы придётся записывать как `fiat`, что хуже;
- неизвестный идентификатор валюты — строка отбрасывается с причиной `unmapped_currency:<raw_id>`, а `raw_id` попадает в `summary.top_unmapped_currencies`. Угадывать по префиксу нельзя;
- неоднозначный алиас (один идентификатор у двух кодов) — ошибка конфигурации: прогон завершается с кодом 2 и сообщением, а не выбирает «первый попавшийся»;
- дубль `code` или невалидный `type` — тоже exit 2.

Домены, наоборот, не требуют реестра: `domain` из CSV уже нормализован (lowercase, ASCII/punycode), не-ASCII домен отклоняется при чтении CSV с понятной ошибкой строки. Это дешевле и предсказуемее, чем тянуть IDNA2008 в рантайм.

## Решение: приведение чисел

Порядок для любого числового поля:

1. Обрезать пробелы по краям, включая неразрывные.
2. Удалить разделители групп, стоящие между цифрами: обычный пробел, `U+00A0`, `U+202F`, `U+2009`, апостроф, `_`.
3. Определить десятичный разделитель:
   - ровно одна `,` и нет `.` → десятичная запятая;
   - ровно одна `.` и нет `,` → десятичная точка;
   - несколько `,` без `.` и шаблон `^\d{1,3}(,\d{3})+$` → группировка, запятые удаляются;
   - несколько `.` без `,` и тот же шаблон → группировка, точки удаляются;
   - всё остальное (включая одновременные `,` и `.`) → `ambiguous_number`, строка отбрасывается.
4. Значение обязано быть конечным `Decimal`. `NaN`, `Infinity`, экспонента — отбрасывание (`non_numeric_value`).
5. Проверки диапазонов из таблицы полей: `rate > 0` (`invalid_rate`), `reserve`/`min`/`max` `>= 0` (`invalid_amount`), `min <= max` (`invalid_limits`), `fee_percent` в `[-100, 100]` (`invalid_fee`).
6. Для опциональных полей пустая строка, `-`, `n/a`, `—` → `null`. Для обязательных — строка отбрасывается (`missing_required_field`).

Строгая трактовка шага 3 (одновременные `,` и `.` → отбрасывание) выбрана сознательно: догадка о локали фида — это скрытая эвристика, которая на одном обменнике даст `1,234` = `1234`, а на другом `1.234`. Ослабление — только новым ADR с тестами.

Форматирование обратно в JSON: `format(Decimal, "f")`, снять хвостовые нули и точку. `0` не превращается в `null` и наоборот; отсутствие данных никогда не кодируется нулём.

## Решение: причина отбрасывания строки

Курс, который не удалось нормализовать, не исчезает молча: он увеличивает `summary.dropped_rate_rows` по причине. Канонический список (расширять — только вместе с ADR):

`invalid_rate`, `invalid_amount`, `invalid_limits`, `invalid_fee`, `missing_required_field`, `non_numeric_value`, `ambiguous_number`, `unmapped_currency:<id>`, `invalid_direction`, `duplicate_rate`.

`duplicate_rate` — повтор ключа `(base, quote, side)` внутри одного документа; остаётся первая строка в порядке документа, остальные считаются отброшенными. Это делает отчёт воспроизводимым (AC-12).

Статус домена от отброшенных строк не зависит: домен `ok`, если из фида извлечён хотя бы один валидный курс (MYSP-2 §2). Отброшенные строки видны в сводке, чтобы «ok с одной парой из двадцати» не выглядел как полный успех.

## Последствия

- `rate` в JSON — строка; любой потребитель обязан парсить её в `Decimal`, а не в `float`. Это записано в контракте, чтобы следующая команда не «упростила» поле до числа.
- Появляется поддерживаемый файл `data/currencies.csv`: его рост — нормальная работа, а не хак. Ошибки в нём валят прогон сразу (exit 2), а не портят отчёт.
- `examples` в отчёте — реальные записи схемы, а не отдельный «урезанный» формат. Тимур проверяет схему на них же.
- Инверсия и сторона сделки фиксируются явно, поэтому позже можно посчитать спред, не перечитывая фиды.
- Схема избыточна для отчёта о покрытии (`side`, `raw`), но не для следующего шага; добавление полей позже стоило бы миграции хранилища.

## Что осталось открытым

- Третье значение `type = metal` требует подтверждения человека (он называл `fiat`/`crypto`).
- `--keep-raw` и политика хранения тел ответов — следующий шаг, если понадобится разбор спорных фидов.
- Подтверждение `side` как части схемы: на AC это не влияет, но фиксирует направление на будущее.
